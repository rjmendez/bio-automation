# Bluesky Social-Posting Pipeline — Hardening & AWS-Migration Audit

Generated 2026-11-04 via a multi-agent workflow audit (4 audit dimensions, 20 independent groundedness
re-checks against the live code, 1 synthesis pass). 18 of 20 findings survived grounding; 2 were dropped
as unverifiable or inaccurate and are not included below.

## 1. Duplicate images

**Within one post: not possible.** `build_obs_index()` resolves each gallery file to exactly one observation id in a dict keyed by relpath (`src/bio_automation/social.py:195-243`, assignment at line 236: `out["files"][rel] = kept.pop()`). `make_draft()`'s image-write loop (`social.py:969`) iterates that already-unique relpath list, and the themed-post builder `make_group_draft()` takes only `rels_of[o][:1]` per observation (`social.py:1199`), with `themes.pick_group()` (`themes.py:216-253`) sourcing obs ids from a dict's unique keys. No code path can place the same file twice in one post.

**Across posts: covered, keyed on observation id.** `duplicate_gate()` (`src/bio_automation/social_state.py:228-242`, pre_send priority 3) withdraws any candidate draft that shares an observation id with another draft already `posted`/`posting` (via `_obs_of()`, lines 87-91, reading the ledger's `obs_id`/`obs_ids`). `check_integrity()`'s `duplicate_post` check (`social_state.py:185-195`) is the ledger-wide backstop, and `ledger_gate()` (lines 211-225, priority 2) blocks *all* posting while any unresolved duplicate exists. `--accept-duplicate` (lines 104-125) records the exact acknowledged draft-id set per observation in `SOCIAL_INTEGRITY_ACK_FILE`; a different duplicate combination re-blocks immediately (line 193). This explicitly covers the single-vs-themed-draft overlap case (see the function's own docstring).

**Real gap: no content-level dedup across different observation ids.** All dedup logic keys exclusively on observation id (`social_state.py:239`, `_obs_of()` lines 87-91) — nothing in `social.py`, `social_state.py`, `social_cleanup.py`, or `social_controls.py` hashes or compares image bytes/relpaths across observations. `build_obs_index()` resolves each relpath to an obs id independently (`social.py:195-243`). If the same physical photo is ever legitimately mapped to two different observation ids upstream (duplicated export across year folders, a stale-but-clean candidate/audit CSV row), the shared-id intersection at `social_state.py:239` is empty and `duplicate_post` never fires (each id appears in only one posted draft) — the same picture could post twice under two different identifications with nothing in this pipeline catching it. This requires a pre-existing upstream labeling/export error to trigger; it is not a bug in the dedup hooks themselves.

## 2. Hardening fixes

**High**
- `src/bio_automation/settings.py:185` — `BSKY_OAUTH_DIR` holds the only copy of the Bluesky private key/session, excluded from backups (`social_state.py:401-405`) and with no Secrets Manager/KMS equivalent; add an automated encrypted off-box backup (or move to Secrets Manager outright) before this becomes the sole irrecoverable asset.
- `src/bio_automation/settings.py:119` (+`social.py:493-501` `Ledger.append()`, `social_rules.py:160-165` `Audit.log()`) — ledger/audit are plain local `open(path,'a')` appends with no cross-process coordination beyond one lock; any multi-host deployment needs these backed by a store with atomic conditional writes.
- `src/bio_automation/social.py:1430` — `ledger_lock`/`byte_range_lock` uses `msvcrt`/`fcntl` OS-local byte-range locking; this cannot coordinate two hosts/containers and must be replaced by a distributed lock before running more than one instance.
- `scripts/windows/register-social-tasks.ps1:36` (`run-social-post.ps1:35-38`, `run-social-prep.ps1:31-34`) — scheduling correctness depends on the named kernel mutex `Global\bio-social-run` with "wait then proceed anyway (log OVERLAP)" semantics; this has no serverless/cron equivalent and must be rebuilt explicitly, not translated 1:1.
- `src/bio_automation/social_controls.py:77` (`read_pause()`) — pause/breaker state is a bare `Path.exists()` check with no lock on the write side; a multi-instance deployment needs this as a shared, strongly-consistent control (and the write path itself locked).

**Medium**
- `src/bio_automation/social.py:283` (`_http_photo`/`fetch_best_photo`) — single `urlopen` call, zero retries on `URLError`/`OSError` (raises `SkipObservation` immediately, line 308-309), unlike `inat.py:40-51`'s retry+backoff for metadata fetches; wrap photo downloads in the same retry/backoff so one transient blip doesn't silently drop an observation from a themed draft (`social.py:1202-1203`, 1209).
- `src/bio_automation/social_state.py:516` (`restore_check()`) — never wired to a `maintenance` hook (unlike `daily_backup`, registered at line 747) or to any scheduled task; register it as a maintenance hook or add it to `Bio-Qdrant-Sync`/a new scheduled task so a corrupt-but-created backup is actually detected.
- `src/bio_automation/social_prep.py:31` (`preflight()`) — hardcodes `C:\` / `D:\` drive checks; replace with a cloud-appropriate check (CloudWatch EBS free-space alarm) or drop entirely once storage moves to S3.
- `src/bio_automation/social_state.py:239` (duplicate_gate's `shared` intersection) — add a content-hash (sha256 or perceptual hash) check across observation ids so a duplicated upstream export can't post twice under different obs ids.

**Low**
- `scripts/windows/run-social-post.ps1:26-27` (and `run-social-prep.ps1:24`) — hardcoded `C:\Python314\python.exe` interpreter path and `F:\services\bio-social\oauth\account.json` session path; parameterize via env/config so they aren't tied to this one machine's drive layout.
- `src/bio_automation/social.py:310` — the `finally: sleep(pause_s)` pacing delay fires even on a failed download that's about to give up with no retry; harmless but wasted — worth revisiting once retry is added above.

## 3. AWS migration plan

**Compute / scheduling.** Replace the three Task Scheduler jobs with **EventBridge Scheduler** rules on the real cadence (03:00 prep, 08:00/12:00/20:00 post, 09:00/13:00/21:00/21:30 watch, 05:00 qdrant-sync — not a generic 08/12/16/20/midnight model). Lightweight steps with no GPU need (`post_next`, watch/alerts/engagement) run as **Lambda** (or short Fargate tasks if runtime exceeds Lambda limits). Reimplement the `Global\bio-social-run` mutex's exact semantics (hold for duration, wait N minutes, proceed-anyway-and-log-OVERLAP) as a **DynamoDB conditional PutItem lock item with TTL**, since OS-level locking (`social.py:1430`) has no cross-host equivalent.

**Local-vision-model dependency.** `social-draft` hard-requires a GPU-resident Ollama (`settings.py:200` `OLLAMA_URL=127.0.0.1:11440`, `_require_gpu()` `social.py:621-625`, no CPU fallback). Two viable paths: (a) reuse the repo's existing one-shot GPU-burst idiom (`cloud/user-data.sh`/`user-data-sam3.sh`: trap-on-exit S3 sync + self-terminate via `instance-initiated-shutdown-behavior=terminate`) to launch a GPU EC2 instance (g5/g6) at prep time that pulls the gallery index + candidate CSVs + model pool from S3, runs `bio social-prep`, pushes the ledger back, and terminates; or (b) stand up a persistent GPU inference endpoint (ECS/EC2 running Ollama behind an internal ALB, or a SageMaker real-time endpoint) and simply repoint `BIO_OLLAMA` at it — the setting is already env-overridable, so this is the lower-effort option and avoids the per-run cold-start/venv-build latency option (a) would add (and correctly, `post_next` never calls Ollama today, so this only affects the drafting step).

**State.** Move ledger/audit/alerts/engagement JSONL (`settings.py:119,143,149,159`) to **DynamoDB** (one item per event, conditional writes replacing `ledger_lock`), optionally streamed to S3 via Kinesis Firehose for the human-readable audit trail. Move backups (`social_state.py:388-460`) to an **S3 bucket with versioning**, keyed by date+uuid (not a local dated-folder listing, which `daily_backup()` checks naively — line 450-460) to avoid the multi-writer collision risk noted above. Move the pause marker (`settings.py:145`, and its already cloud-friendly sibling `SOCIAL_PAUSE_SYNC_FILE`, line 148) and circuit-breaker state to an **SSM Parameter** or DynamoDB item checked by each scheduled Lambda before posting. Actually wire `restore_check()` (`social_state.py:516`) as its own scheduled EventBridge/Lambda job against the S3 backup bucket.

**Secrets.** Move the Bluesky OAuth private key/session (`settings.py:185,193`) into **AWS Secrets Manager** (KMS-encrypted at rest); tasks fetch via IAM role + `GetSecretValue` at runtime instead of reading a local directory that exists on one machine today with no durable copy.

**Image storage.** Move `GALLERY_DIR` (`settings.py:34`) to an **S3 bucket** preserving the existing `<year>/<year-month>/` key structure; access via S3 directly or a Mountpoint-for-S3/EFS cache layer so `draft.json` image references and the hashing/posting code don't need a full rewrite. (Note: `settings.NAS`/`Y:\Bio`, `settings.py:38`, is unused anywhere in the social path — no drive-letter dependency to migrate there; the real coupling is whoever populates `GALLERY_DIR` and the candidate CSVs on `D:`, outside this pipeline's scope.)

## 4. Dropped / not covered

The audit could not verify two areas with confidence: whether the local drafts directory / image-file path assumptions baked into draft hashing and posting pose a further portability risk beyond what's noted above, and whether `QDRANT_SYNC_MARKER`/`GALLERY_TITLE_CACHE`/`GALLERY_OBS_INDEX` (small local JSON caches) have multi-writer protection — these were flagged by an audit agent but a verification pass found the specific sub-claims inaccurate (e.g. `sync_marker.py` does have its own `byte_range_lock`), so they're excluded above rather than presented as fact.
